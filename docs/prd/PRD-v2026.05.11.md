## 2. 后续版本：复盘与自我迭代机制

### 2.1 产品目标

后续版本中，系统应具备通过复盘持续提升判断质量的能力。

核心目标不是让系统更频繁地推荐机会，而是让系统：

- 少犯重复错误。
- 更理解用户的交易风格。
- 更清楚哪些信号对用户有效。
- 更谨慎地区分真实能力、噪音和运气。
- 把成功和失败案例沉淀为可讨论、可确认、可追溯的改进建议。

该机制的长期定位是：

> 让产品从“每天给出交易判断”逐步进化为“帮助用户建立个人交易判断系统”。

### 2.2 核心原则

复盘与自我迭代机制必须遵守以下原则：

- 所有重要判断必须可追溯，不能只保存最终结论。
- 复盘评价的是决策质量，不只是价格涨跌结果。
- 成功案例也必须复盘，避免把运气误认为规则能力。
- 失败案例必须区分规则错误、数据不足、突发事件和执行偏差。
- 系统只能提出改进建议，不能未经用户确认自动改变核心交易规则。
- 用户确认后的改进才可以沉淀为规则、配置或分析框架更新。
- 改进目标是提高高信噪比判断能力，而不是追求更多推荐。

### 2.3 决策快照

为了避免事后归因偏差，系统在给出重要判断时应保存决策快照。

决策快照至少应包含：

- 标的代码。
- 判断日期和依据数据时间。
- 原始建议：不操作、观察、小仓试探、加仓、减仓、止盈、退出。
- 当时的核心理由。
- 当时的关键价位。
- 当时的失效条件。
- 预期观察周期，例如 1 个交易日、5 个交易日、20 个交易日。
- 当时宏观市场状态。
- 当时技术面状态。
- 当时基本面、新闻或财报状态。
- 当时使用的规则版本。
- 当时使用的数据更新时间。

决策快照的目的不是记录所有市场信息，而是保留足够上下文，让未来复盘能够判断：

- 当时为什么做出这个判断。
- 当时是否有足够依据。
- 后续结果是否真的能证明原判断有效或无效。

### 2.4 复盘触发

系统应根据判断类型自动生成待复盘事项。

候选触发节奏：

- 短线反弹机会：1、3、5 个交易日后复盘。
- 财报后机会：1、5、20 个交易日后复盘。
- 长期加仓或减仓判断：20、60 个交易日后复盘。
- 止盈或退出判断：5、20 个交易日后复盘。
- 不操作判断：在后续出现显著行情时进行抽样复盘。

不操作也应该进入复盘体系。

原因是：

- 避开坏机会是一种成功。
- 错过高质量机会是一种需要学习的失败。
- 系统保持安静的能力，与系统发现机会的能力同样重要。

### 2.5 复盘评价维度

复盘不应只判断“涨了还是跌了”。

每次复盘至少区分三个层面：

1. 结果是否正确

   例如价格是否按预期方向运行，是否跑赢或跑输 SPY、QQQ、BTC、行业 ETF 等合理基准。

2. 过程是否正确

   例如当时的宏观、基本面、技术面、情绪和风险判断是否合理，是否遗漏了重要信息。

3. 执行是否一致

   例如用户是否真的执行了建议，是否提前追高、过早止盈、没有遵守失效条件，或根本没有操作。

复盘时需要避免简单结论：

- 判断正确但亏钱，不一定代表系统错。
- 判断错误但赚钱，不一定代表规则有效。
- 不操作后上涨，不一定代表系统漏掉机会。
- 止盈后继续上涨，不一定代表止盈规则错误。

系统需要解释：这次结果主要来自能力、运气、风险控制、市场噪音，还是意外事件。

### 2.6 复盘输出

复盘结果应以可读卡片形式呈现，重点服务用户讨论和确认。

示例结构：

```text
TSLA 复盘
原始建议：小仓试探
观察周期：5 个交易日
结果：上涨 7.8%，跑赢 QQQ 4.1%

当时判断：
- 跌到个人关键价位附近
- 大盘风险未继续恶化
- 基本面负面新闻未证伪长期逻辑

复盘结论：
这次判断质量较高，核心有效信号是“关键价位 + 恐慌释放 + 未跌破前低”。

可改进点：
下次类似场景中，可以提高“关键价位附近止跌”的权重，但仍需保留大盘破位过滤。
```

复盘卡片应尽量输出：

- 原始判断。
- 实际结果。
- 相对基准表现。
- 判断质量评价。
- 成功或失败的主要原因。
- 是否存在数据缺口。
- 是否存在规则改进建议。
- 是否需要用户确认沉淀。

### 2.7 改进建议与用户确认

系统可以在复盘后提出改进建议。

建议类型包括：

- 提高或降低某类信号权重。
- 新增硬排除条件。
- 修改某个标的的个人关键价位。
- 调整某类资产的观察周期。
- 调整短线机会与长期持仓的优先级。
- 将某个失败案例加入反面样本。
- 将某个成功案例加入正面样本。
- 建议在 Dashboard 增加某类提醒。

但所有改进建议默认进入“待确认”状态。

用户可以选择：

- 接受。
- 拒绝。
- 暂缓。
- 只记录，不改变规则。

只有用户接受后，改进建议才能影响后续分析。

### 2.8 不应做的事情

复盘与自我迭代机制不应演变为：

- 自动下单系统。
- 未经确认的自动调参系统。
- 因为短期涨跌而频繁修改规则。
- 为了提高胜率而推荐更多低质量机会。
- 使用无法解释的黑盒模型替代原本可解释的交易判断。
- 用单个案例覆盖长期产品原则。

尤其要避免：

> 因为一次错过机会，就让系统变得更激进。

产品的核心仍然是高信噪比、可解释、克制的交易决策辅助。

## 3. 与现有 Phase 的关系

建议将复盘与自我迭代机制放在 MVP 完整闭环之后。

前置依赖：

- Dashboard 已经能稳定生成每日判断。
- 系统已经保存每日历史报告。
- 重要判断已经具备依据日期、数据版本和规则版本。
- 已经有基本的计划状态追踪，例如接近、触发、失效、仍有效。

建议 Phase 关系：

- Phase 1：不实现，只保留未来扩展意识。
- Phase 2：不实现，但 Dashboard 判断应尽量包含依据日期和核心理由。
- Phase 3：不实现，但 AI 解释层应保留可追溯输入。
- Phase 4：开始保存每日历史报告，为复盘打基础。
- Phase 5 或更后：实现历史判断与表现追踪。
- Phase 6 或更后：实现复盘与用户确认式自我迭代。
