# 线上 QA 问题清单

用途：本文件可直接复制给主 Agent，用于修复本轮线上 QA 发现的问题。修复时仍需先阅读 `AGENTS.md`、PRD 和最新技术计划，并保持当前 phase 边界。

当前项目状态为：

- Phase 2 Dashboard v1 准备中。
- Production `/api/health` 返回 `status: ok`。

## P0：Settings 保存/停用后跳回登录页，阻断配置维护

### 复现步骤

1. 打开 Production。
2. 输入正确访问密码并进入应用。
3. 进入 `/settings`。
4. 添加一个持仓。
5. 对已存在持仓点击“保存”或“停用”。

### 实际结果

点击“保存”或“停用”后，页面跳回 `/login`。

### 期望结果

保存或停用成功后仍停留在 `/settings`，并显示更新后的配置状态。若 session 失效，应显示明确提示并在重新登录后回到原路径。

### 影响

这是当前 Phase 1 的核心路径。用户无法可靠维护持仓、关注列表、关键价位，配置页的编辑闭环被打断。

### 初步判断

`/settings` 在 `src/app/(protected)/layout.tsx` 中通过 cookie token 保护；保存/停用是 Next server action 表单提交。提交后的重新渲染阶段如果没有正确读到 cookie，会触发 `redirect("/login")`。当前 redirect 也没有携带 `next=/settings`，用户上下文丢失。

### 建议修复方向

- 优先复现并修复 server action 提交后的 auth/session 识别问题。
- 在受保护路由 redirect 时保留目标路径，例如 `/login?next=/settings`。
- 对保存、停用、刷新数据等 server action 成功后显式回到 `/settings` 或返回可控状态。
- 如果 session 失效，给出明确提示，而不是无解释地跳回登录。

### 回归测试点

- 新增持仓后点击保存，不跳回登录。
- 新增持仓后点击停用，不跳回登录。
- 关注列表保存/停用不跳回登录。
- 关键价位保存/停用不跳回登录。
- 刷新数据后不跳回登录。
- 重新登录后能回到原本访问的 `/settings`。

## P1：移动端顶部导航溢出，退出入口不可见

### 复现步骤

1. 使用 390px 宽度视口打开 Production。
2. 登录后进入首页。
3. 查看顶部导航。

### 实际结果

顶部导航只可见 `Settings`、`Health`，`退出` 图标被挤出可视区域。

### 期望结果

移动端仍能看到并点击退出入口。导航不应横向溢出或遮挡。

### 影响

用户在手机上无法明确退出登录，影响安全感和基础可用性。

### 建议修复方向

- 移动端将导航改为 icon-only。
- 或使用可换行导航、更多菜单、紧凑按钮。
- 保证 360px、390px、414px 宽度下 `Settings`、`Health`、`退出` 都可访问。

### 回归测试点

- 390px 宽度下退出入口可见可点。
- 360px 宽度下导航不横向溢出。
- 点击退出后回到登录页。

## P1：首页仍显示 Phase 0 工程地基，`/dashboard` 为 404

### 复现步骤

1. 登录 Production。
2. 打开 `/`。
3. 直接访问 `/dashboard`。

### 实际结果

首页仍显示 `Phase 0 / 工程地基`。`/dashboard` 返回 404。

### 期望结果

当前项目已进入 Phase 2 Dashboard v1 准备阶段，首页至少应准确表达当前阶段。若 Dashboard 尚未实现，应给出“Dashboard v1 准备中”或展示 Phase 1 数据状态入口，而不是停留在 Phase 0。

### 影响

用户和后续 agent 容易误判线上状态，以为 Phase 1 没上线或 Dashboard 路由损坏。

### 建议修复方向

- 在 Dashboard v1 未完成前，将首页改为 Phase 1 数据状态与配置入口。
- 或增加 `/dashboard` 占位页，说明 Dashboard v1 准备中，并链接到 `/settings`。
- 文案同步为当前阶段，不再显示 Phase 0。

### 回归测试点

- 首页阶段文案与 `AGENTS.md`/技术计划一致。
- `/dashboard` 不返回默认 404。
- 未实现的功能应有明确说明和下一步入口。

## P2：未登录访问受保护页不会保留目标路径

### 复现步骤

1. 未登录状态直接访问 `/settings`。
2. 被重定向到 `/login`。
3. 输入正确密码。

### 实际结果

登录后进入 `/`，没有回到 `/settings`。

### 期望结果

登录后回到最初访问的受保护路径。

### 影响

用户从收藏、手机书签或 QA 链接进入配置页时，需要二次导航。

### 建议修复方向

- 受保护页面 redirect 到 `/login?next=<current-path>`。
- `api/login` 已有 `next` 处理与外部 URL 清洗，应复用该能力。

### 回归测试点

- 未登录访问 `/settings`，登录后回到 `/settings`。
- 未登录访问 `/health`，登录后回到 `/health`。
- `next=https://evil.example` 不会产生外部跳转。

## P2：停用操作缺少确认或撤销

### 复现步骤

1. 进入 `/settings`。
2. 对持仓、关注标的或关键价位点击“停用”。

### 实际结果

从页面结构看，停用是直接 submit，缺少确认或撤销。

### 期望结果

停用前应有确认，或停用后提供明确反馈与撤销路径。

### 影响

容易误停用生产配置。虽然是软停用，但用户心智上仍属于破坏性操作。

### 建议修复方向

- 增加确认弹窗或二次确认。
- 成功后显示“已停用”反馈。
- 可考虑短时间撤销。

### 回归测试点

- 点击停用前出现确认。
- 取消确认不会改变数据。
- 确认停用后记录不再作为 active 配置展示。

## P2：基础偏好配置未出现在设置页

### 复现步骤

1. 打开 `/settings`。
2. 检查页面模块。

### 实际结果

页面包含持仓、关注列表、关键价位和数据刷新状态，但未看到基础偏好配置。

### 期望结果

如果 Phase 1 验收包含基础偏好配置，应在设置页提供最小偏好入口；如果当前不实现，应更新文档并明确延期。

### 影响

PRD/技术计划与线上功能存在验收口径偏差。

### 建议修复方向

- 补充最小基础偏好配置。
- 或更新 PRD/技术计划/AGENTS 当前状态，明确基础偏好配置暂未实现。

### 回归测试点

- 设置页有基础偏好配置入口，或文档明确说明暂不包含。

## P3：表单数字字段缺少前端约束和字段级错误反馈

### 复现步骤

1. 打开 `/settings`。
2. 在成本价、关键价位、关注优先级等字段输入无效数值。
3. 提交表单。

### 实际结果

服务端有 schema 校验，但页面层面缺少明显的 `min/max` 约束和字段级错误反馈。

### 期望结果

用户在提交前或提交后能看到具体字段错误。

### 影响

无效输入时用户可能只看到提交失败或页面异常，不知道如何修正。

### 建议修复方向

- 成本价、关键价位设置 `min="0"`。
- 优先级设置 `min="0"`、`max="100"`。
- 捕获 server action validation error 并展示字段级中文错误。

### 回归测试点

- 负数价格无法提交或显示明确错误。
- 超出范围优先级显示明确错误。
- 错误反馈不泄露内部异常堆栈。

## 漏测复盘

本轮初始 QA 漏掉了 P0 问题：用户在 `/settings` 中添加持仓后点击“保存/停用”会跳回登录页。

原因：

- 初始测试验证了登录、错误密码、首页、健康 API、只读 settings 页面和移动端，但没有完成“新增后继续保存/停用”的二次交互。
- 自动化浏览器出现 cookie 持久化限制后，测试转向直接 HTTPS 读取 settings HTML，导致真实浏览器中的 server action 提交闭环没有被覆盖。
- 把“能读取 settings 页面”和“settings 编辑闭环可用”混在了一起，这是 QA 设计不足。
- 对配置页的核心用户行为建模不够完整：新增只是第一步，保存、停用、刷新后的会话保持才是闭环。

改进：

- 后续 QA 必须覆盖新增后的保存/停用。
- 对所有 server action 表单，都要验证提交后是否仍在预期页面。
- 如果浏览器自动化受限，必须明确标记“未完成真实点击闭环”，不能用 API/HTML 读取替代。
- 已将该要求写入 `docs/process/QA-AGENT.md` 和 `docs/qa/ONLINE-QA-REGRESSION-v2026.05.12.md`。
